# 客诉管理原型使用说明

2026-10-06：保留现有页面，统一规则配置与工单运行逻辑。当前入口以本说明为准，仓库内旧版流程文档仅供历史追溯。

## 打开方式

直接打开项目根目录 `zuhu.html`，进入“客诉管理”的客诉工单、规则配置、演示入口。也可在项目根目录运行 `python3 -m http.server 8765 --bind 127.0.0.1`，打开 `http://127.0.0.1:8765/zuhu.html#complaint-tickets`。本地文件与 HTTP 属于不同存储来源，不会互相搬运数据。

## 唯一运行链路

- `workflow/app.js` 保留 PC、员工 H5、审批和付款表单；`workflow/engine.js` 负责统一工单状态流转。
- `rules-app.js` 复用现有规则列表、指派与岗位表单、审批画布；规则样式和菜单路径保持原样。
- `configuration.js` 负责配置初始化、规则快照、实际节点分配及审批解析；复用 `rules.js`、`node-assignment.js` 和 `approval-flow.js` 的配置能力。
- `shared-store.js` 统一持久化、迁移与版本冲突校验。两类页面均读写 `meiye.complaint.unified.v1`，不再各自维护生效规则。
- 旧 `workflow/#/rules` 入口转到现有唯一规则编辑器；旧根目录工单入口转到统一工单页。根目录旧 `app.js`、`engine.js`、`store.js`、`refunds.js` 不再由当前页面加载，保留用于历史模型核对和迁移测试。

## 配置如何生效

新建工单按等级唯一匹配启用场景，并保存场景版本、审批配置、节点策略和时限快照。未启用对应等级或同等级多条启用规则时明确报错，不隐式选择第一条。现有受理页只选等级，因此新建同等级替代规则须先设为停用，切换时停用原规则再启用新规则。

节点指派和岗位人员仍沿用页面现有的全局配置范围；办理时效及方案审批按场景配置。首联、处理、付款和回访实际使用所配人员、轮排、最少待办、沿用或手动分派。岗位当前有效成员用于人员解析，策略采用工单快照。轮排游标随成功保存的业务动作更新，规则预览不消耗名额。付款必须由有效财务人员办理，无有效人员或兜底时阻止操作并提示维护规则。

提交方案使用该工单审批模板快照，按方案类型、金额条件和当前组织岗位解析审批人；支持会签、或签、依次审批及抄送。各审批节点采用自身时限。付款与回访分别按节点指派，主负责人不会随付款人和回访人变化。回访配置允许沿用前序人员时按配置执行，不额外强加独立回访制度。

主状态保持待分派、待首联、处理中、待方案审批、待打款、待回访、已结案。客户在提交方案前认可，审批通过后有款项进入付款，无款项进入回访。没有增加接单、审批后再确认或独立服务执行表单。

配置中的独立服务执行节点目前没有对应的可操作任务；分派节点也不新增受理步骤，手动分配使用目标节点所配的分派负责人。它们是仍需结合实际产品流程补齐的原型能力，不宣称本次已实现。风险词、金额分级等原有固定演示策略继续保留；被移除的隐藏编辑页不再是第二个配置入口。

## 数据和兼容

首次打开自动读取原工单存储 `meiye.complaint.reference.v4` 和原规则存储 `meiye.complaint.prototype.a.v1.workflow3`（兼容更早规则键），合入统一记录。原键原样保留，不被删除或覆盖；后续以统一记录为准。

当前工单保留既有规则快照、审批、期限、凭证及记录，新配置不追溯改写。更早旧引擎的 `cases` 保存为历史档案，旧详情链接可只读查阅，不自动猜测并转换其未完成任务。不要重置浏览器存储来处理迁移问题；无法解析的数据会报错并保留原值。

页面使用共享版本号和可用的 Web Locks 防止跨页覆盖。发生版本冲突时刷新后重新提交。演示重置保留已保存的规则配置，仅恢复工单样例。
