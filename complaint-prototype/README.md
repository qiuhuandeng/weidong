# 客诉管理原型使用说明

## 2026-10-07 多项目退款与完整方案详情

PC／H5 的确认方案与只读详情共用同一份结构化数据，沿用原有蓝白配色。PC 抽屉按方案类型、订单退款、额外赔偿、置换商品、收款信息和方案依据分区，只显示当前类型需要的内容；H5 为独立页面与分区卡片。两端底部固定合计与确认操作，商品价值单独显示，不加入现金应付款。

- 同一订单可勾选多个退款项目，各自填写金额或选择“全额”。PC 支持全选，H5 点击项目卡片勾选后展开金额输入。取消勾选不计入退款和提交明细，再次勾选保留本次填写金额。逐项目校验可退上限，并校验整单余额；未选项目和未填金额不能作为退款方案提交。
- 退款门店与业绩归属在明细下方填写。赔偿明确为额外支付的金额，组合方案底部显示退款＋赔偿拆分。收款方式使用银行卡／支付宝／微信切换，银行卡显示开户银行。
- PC 商品置换使用表格；H5 使用卡片、数量加减和底部商品搜索面板。支持多个商品、名称搜索、删除及实时汇总，新增商品不填写备注。
- 工单“处理方案”按实际类型完整展示订单号、退款项目名称／数量／实付／本次退款、退款门店与业绩人员、赔偿金额、置换商品单价／数量／价值、收款信息及方案依据。PC 明细为只读表格，H5 为无横向滚动的明细列表，默认展开已有方案。保留历史商品备注；没有项目拆分的旧方案保留原金额并明确提示未记录拆分明细；直接结案无方案时显示实际处理结果。
- 示例版本升为 7，共 62 种情况。增量补入 `KS20261007-P40`（两个项目退款 300＋200 元，赔偿 100 元）和 `KS20261007-P41`（两个项目退款合计 500 元，另置换修护霜 2 件、面膜 1 件，总价值 480 元）。均从待付款可继续办理，P41 付款后进入采购。原工单记录、已完成操作与规则配置保留。

## 2026-10-07 PC 表格与 H5 移动表单

列表操作列仅保留“查看详情”，分派保留在详情抽屉中；直接结案归入详情“更多”菜单，原办理条件不变。

## 2026-10-07 PC／H5 工单操作与处理方案

本节是当前办理口径，替代下方历史记录中的人工转门店协同、先采购后付款和仅末节点结案等说明。

- PC 与 H5 移除转门店协同、反馈与撤回入口。新工单按来源进入已配置的首办路径：CRM 直接售后；400／经理热线、微信／企微先门店。门店须记录有效沟通，已解决可直接结案，未解决填写原因后转售后。售后仍须补充自己的有效联系记录，首次联系时间与整单期限保留。
- 结案不只看状态：门店／售后当前办理人已有效联系客户，且无未完成退款、赔偿、置换事项时，可在“处理中”直接结案。待定级、待派单、尚未有效联系、挂起及其他部门办理阶段不能越过待办结案；“待结案”由售后负责人核实履行结果后确认。
- “待处理／待派单”保留分派操作。分派负责人或售后经理可在开派时间前选择有效售后候选人、填写原因提前分配；不消耗自动轮排顺序，不重置整单期限，首次联系计时从实际分配起算。
- 退款先选择客户本人订单，展示项目数量、实付、已退和可退金额，逐项填写退款，自动汇总。记录退款所属门店、该店有效的退款业绩归属人员。确认方案时检查订单及项目余额和其他工单占用；成功付款时再次校验并更新订单和项目已退金额。
- 赔偿独立为“额外赔偿”，表示订单退款之外额外支付的款项。“退款＋赔偿”清楚显示退款合计、额外赔偿、应付款合计；商品价值不计入应付款。收款方式支持银行卡、支付宝、微信，需填写收款人、账号，银行卡另填开户银行。
- 商品置换通过商品选项添加多条明细，每条填写数量，展示单价、小计和总价值。采购结果表单保留商品及备注，要求记录采购／交付结果并确认完成。
- 默认新增配置与新增工单示例中的资金加置换路径为：售后方案确认 → 配置的部门审批（如有）→ 付款办理 → 采购办理 → 售后结案。纯置换跳过款项分支。采购是办理节点，不增加采购审批。

`ticket-operations.js` 提供两端共用的门店首办、直接结案、提前分派和方案明细逻辑，`solution-flow.js` 继续执行已确认方案的后续任务。旧方案保留可读及付款能力，新表单保存结构化订单、项目、收款信息和商品明细。旧人工门店协同中的工单恢复原售后办理，保存历史与原时限；其他在途工单沿用已有快照，不重置用户已处理的示例。示例版本为 7，62 种情况；旧浏览器新增以下独立工单即可验收新流程，无需清空存储。

## 2026-10-07 规则首联时限与节点设置

新建／编辑规则只保留一个“首次联系时限（小时）”，与“整单时限（小时）”同一行等宽展示，两者下方不显示说明文字。门店、售后共用同一个首联时限；各办理节点不再显示首联时限输入，只保留节点办理时限。首联时限范围为 0.25—720 小时，不超过整单时限。统一字段沿用原 `firstContactHours` 值，删除独立门店首联字段；保存后用于新工单，在途快照和已开始的计时不重置。

门店办理的办理人来源仅保留“工单所属门店负责人”和“客户的接待老师”，首办与后续门店节点保持一致。接待老师按关联订单、工单或客户档案中的人员标识匹配；缺失、停用或跨门店的人员不承接，保留待分派，维护关联资料后由经理重试。新编辑配置不再使用岗位分配、指定人员或人工兜底人员，旧人工指派配置迁为所属门店负责人；在途快照保留原配置。

门店结案和售后结案不再显示结案人员配置，沿用对应门店办理人或工单售后主负责人。添加菜单仅显示办理节点、审批节点、条件分支、抄送节点；门店结案、售后结案通过办理节点的类型选择。最下方添加按钮位于结案路径的汇合线下方、“工单已结案”上方，同一段连线保留一个添加入口。

## 2026-10-07 流程配置修正：当前等级规则与可编辑条件树

本节为当前配置口径，替代此前单独绘制的来源示意图。规则列表先按 AI 定级匹配等级场景，进入规则后不再判断客诉等级。

流程起点恢复为“工单创建 → AI 定级 · 当前级别（匹配当前场景名称）”。1—4 级规则只配置一个公共的售后专员办理节点，5 级规则只配置售后经理办理节点，不同时展示两类售后节点。修改规则等级时，承接角色随等级更新，保留原节点时限、来源分支及后续配置。

| 工单来源 | 发起口径 | 默认首办路径 |
| --- | --- | --- |
| 400客服 / 总经理热线 | 两个坐席分别接听，由 400 客服统一发起 | 工单所属门店首次办理 |
| CRM系统 | 门店店长、市场部、销售部；门店 / 网咨发起，已沟通但未解决 | 当前等级规则的售后办理节点 |
| 微信小程序 / AI企微 | 客户点击链接自助提交 | 工单所属门店首次办理 |

条件分支的判断方式为“工单来源 / 门店处理结果 / 适用方案类型”，不再提供客诉等级。来源支持以上三组选项多选；门店结果支持已解决、未解决；方案类型沿用七类方案与金额条件。可编辑名称、选项和优先级，可添加、复制、删除分支及其中的节点。默认分支显示未被前面条件覆盖的来源或结果。

默认树：非 CRM 来源条件 → 门店首次办理 → 门店结果条件：已解决 → 门店直接结案；未解决 → 汇入公共售后节点。CRM 默认分支直接汇入同一个售后节点。售后跟进、确认线下已沟通的方案后，进入方案条件控制的后续部门审批、门店履约、付款及客服结案。

门店直接结案是可编辑的真实终止节点，保存于流程树，路径解析遇到该节点即结束，不再执行后续售后和付款节点。画布的连接线根据节点布局生成：提前结案的分支保留独立列，从结案节点正下方垂直连至最下方“工单已结案”之前再汇合；后续节点不占用该列，不再向外侧折返避让。只有实际分叉和汇合处使用横向连接，嵌套分支、新增结案出口及缩放均按同一规则布局。门店结案通过办理节点类型添加；校验要求门店首办在前，且结案之后不能再安排节点。

所有可编辑配置统一保存于 `ticketFlow.nodes`（`schema: 2`），不再使用独立的 `entryRouting`。已有入口设置在打开编辑草稿时迁入普通分支，保留当前等级的售后节点、门店人员及时限和公共后续配置。旧等级条件按该规则等级消解，保留有效路径与原方案条件优先级。保存后生效；不修改在途工单快照、跟进记录、订单或挂起记录。

流程配置工具栏只保留缩放控件，“查看流转路径”按钮及抽屉入口已移除。条件匹配仍由实际配置树决定，保存刷新后保持一致。

画布卡片宽度由 300 缩至 240 像素，标题区、内容内边距、节点间距同步收紧；长条件在卡片内显示两行，悬停或打开配置可查看完整条件。缩放按整张图等比缩放，不再拉伸列间距。单一继续路径跨过嵌套条件组时，仅保留分支内的一个添加按钮，移除同段直线上的重复入口。

办理类型统一为六类：门店办理、售后办理、付款办理、门店结案、售后结案、采购办理。门店首办与后续门店办理使用同一类型；售后专员和经理使用同一类型，仍按规则等级配置人员。门店结案沿用首次办理时限，保存为直接结束路径。审批和抄送仍使用各自节点设置。

售后办理后新增真实、可编辑的“涉及商品置换”条件分支，匹配商品置换、退款+商品置换、赔偿+商品置换三类方案：匹配时进入采购办理，其他方案走默认分支；汇合后继续原有款项条件、部门审批、付款与售后结案。默认纯置换路径为售后办理 → 采购办理 → 售后结案；含退赔的置换方案先采购，再走原款项流程。节点和条件均可修改、保存，采购支持岗位轮排或指定采购人员、兜底人员与独立办理时限。

岗位人员新增“商品采购岗 / 顾欣 · 采购专员”。旧配置只补齐一次，后续人员停用、岗位修改或删除不会被刷新重置。旧规则仅在编辑草稿中补入采购分支，保存后用于新工单；在途快照保留原流程。已经编辑删除过的采购分支不会反复自动补回。

PC/H5 共用采购办理表单：查看方案商品、数量、单价和总价值，填写采购结果，可补充采购／交付单据号及附件，确认本节点采购事项完成后流转到下一节点。仅当前有效采购办理人可提交；缺人时保留方案，由经理维护人员后重试。采购期间工单状态仍为“审批中”，当前环节为“采购办理”，节点到达时开始计时。

## 2026-10-07 当前口径：六个工单状态、独立办理环节

以本节为当前功能说明；下方第一至第三步、配置阶段章节保留实施记录，历史状态名称不再作为当前工单状态。

整条业务流程为：工单创建 → AI 定级（不明确时由售后经理确认）→ 匹配场景规则及派单 → 售后首次联系与跟进 → 录入线下已沟通确认的解决方案 → 按规则执行后续部门审批、门店办理、付款办理等节点 → 售后主负责人线下核实各事项完成并手动结案。分支判断读取客诉等级或七种方案类型；方案确认完成售后节点，不新增方案审批申请。

| 工单状态 | 范围 | 当前环节与待办示例 |
| --- | --- | --- |
| 待处理 | 工单已创建，售后尚未开始跟进 | 定级确认、规则匹配、等待当班售后派单、首次联系客户 |
| 处理中 | 售后联系客户、调查问题、协商和填写方案 | 首次保存跟进即进入，包括未接通；临时门店协同、审批驳回或付款退回售后也归于此状态 |
| 审批中 | 方案确认后，工单进入后续部门流转 | 部门审批、正式门店办理、付款办理；付款失败继续留在此状态 |
| 待结案 | 后续需要的节点全部完成，等待客服核实并手动结案 | 无退赔、退款、赔偿、商品置换及各组合方案均需客服确认结案 |
| 已挂起 | 售后暂时暂停办理 | 显示挂起原因、原办理阶段与恢复操作；暂停节点计时，整单继续计时 |
| 已结案 | 售后确认结案后 | 保留完整方案、审批、付款、商品交付及办理记录；旧合并记录归入此状态，并保留主工单链接 |

主流程：待处理 → 处理中 → 审批中 → 待结案 → 已结案。“审批中”是后续部门流转的工单状态，包含办理节点，不增加解决方案审核。没有后续部门节点时，确认方案后直接进入待结案。临时门店协同属于售后调查环节，保持处理中；配置流程中的正式门店办理属于审批中。同部门转派保持原状态；挂起恢复回到此前状态。

PC 与 H5 的状态筛选、状态标签使用同一套六状态，顺序为待处理、处理中、审批中、待结案、已挂起、已结案。列表和详情同时展示当前环节与办理人，更多筛选／H5 筛选可按环节查询。打开详情不改变状态；保存未接通跟进会进入处理中，但不伪造有效首联、不重置首联时限，也不能直接确认尚未沟通好的方案。

数据字段：`ticket.state` 为六状态之一；`ticket.phase` 为内部办理阶段，结合 `execution` 当前节点、挂起及协同记录决定操作。`ticket-lifecycle.js` 统一同步状态、环节、待办及提醒，阻止旧接口绕过当前节点。后续节点缺少人员时，状态仍按所处节点保留审批中或待结案，显示人员待匹配；不退回新工单的待处理状态。

原四状态记录刷新时按实际进度重算，保留编号、流程快照、处理记录、付款、截止时间和已完成的示例结果。示例数据版本升为 4，仅追加缺失的固定编号工单，不覆盖已有记录；再次刷新不重复追加或产生无意义的存储版本变化。

已清理当前 PC/H5 的“待方案审批、待打款、待回访”选项、旧回访表单、撤回方案入口及独立结案风险复核。后续审批只按配置节点执行，付款后返回客服结案；跟进中提及风险关键词只记录信息，不再通过旧硬编码规则静默改级、替换流程或强加结案复核。旧回访入口地址兼容打开客服结案场景，不再重新生成旧流程工单。

## 2026-10-07 当前挂起管控

仅售后办理环节允许挂起，节点配置的挂起开关继续生效。客服每张工单最多自主挂起 1 次，累计最多 24 小时；次数与时长随整张工单保留，转派、审批驳回、付款退回、重新提交方案均不重置。超出额度、再次挂起或延长，须由同部门有效售后主管操作并填写依据。

挂起必填原因类型（等待客户补充必要资料／客户约定稍后联系／等待外部机构必要材料）、具体说明及未来的恢复时间；关联沟通记录与上传依据至少提供一项。关联记录保存快照，原记录变更不影响审计。客服忙、下班、内部审批、正式门店办理、付款等待均不作为挂起类型。

到期自动恢复原节点与办理状态，不完成节点、不推进流程。暂停时长只计至约定恢复时间；晚于到期时间打开页面，多出的时间继续计入有效办理耗时。原型通过页面加载及每 15 秒维护检查执行，页面关闭期间不运行后台任务；重新打开时按照原定到期时间补算。正式系统需要服务端定时任务及通知服务承接实时执行。

主管可提前恢复、延长或纠正挂起。延长保存原恢复时间、新时间、操作者和依据；纠正为“原因不成立”后立即恢复，本次挂起时间全部计入有效办理耗时，不抹除挂起记录或返还自主次数。节点挂起前已超时的事实保留，挂起时继续展示并纳入超时筛选；整单时限不受挂起影响。

PC/H5 详情增加“办理时效与挂起记录”，展示当前节点总耗时、有效办理耗时、暂停时长、已完成节点耗时及整单累计挂起次数／时长。原有历史节点根据已有时间字段还原，无法还原的更早节点不补造记录。列表展示正在挂起的原因、时长和自动恢复时间，并支持按原因、正在挂起、多次挂起、临近超时、原因不成立、累计超过 24 小时筛选。

工单列表的“挂起管理”提供售后主管视角，统计每位客服的挂起工单比例、次数、时长、临近超时挂起和原因不成立次数。比例分母为该客服曾负责的工单，转派前后均保留负责记录；主管代办挂起计入当时主责客服。临近超时按剩余节点时限不超过 1 小时（含已超时）标识，作为复核线索。点击“主管查看”进入该工单的主管办理视角，离开后恢复原入口身份。

原已恢复的挂起历史保留。旧在途挂起缺少有效恢复时间时，以挂起起点加 24 小时设定上限；客服原预计时间超过上限的按上限校准，旧主管的有效恢复时间保留。原始字段保存在 `legacy`，类型标为历史挂起，不虚构依据；已经到期的恢复并留痕。

核心逻辑在 `suspension-control.js`，PC/H5 共用表单与展示在 `suspension-ui.js`。额度暂按已确认的 1 次／24 小时固定；当前未增加可配置额度的后台页面。

## 配置如何生效

新建工单按自动定级或经理确认的等级唯一匹配启用场景，并保存场景版本、审批配置、节点策略和时限快照。未启用对应等级或同等级多条启用规则时保留工单并提示原因，不隐式选择第一条。新建同等级替代规则须先设为停用，切换时停用原规则再启用新规则。

岗位人员在全局页维护，流程中的节点分别配置来源、人员与时限。新工单先按售后办理节点与排班分配；方案确认后由 `solution-flow.js` 执行整单流程。部门审批、门店办理、付款办理和客服结案分别产生任务，具体表单与动作见上方第二步说明。旧在途记录已经由 `ticket-lifecycle.js` 衔接当前节点执行，不再开放旧方案审批与回访操作。

条件选择使用工单等级和确认方案，节点有效人员在到达节点时解析，规则版本沿用工单快照。轮排只在成功分派时前进；付款节点只能由有效财务人员办理。没有有效人员时保留任务并显示原因，维护人员后重试，不把异常节点当作完成。结案保留售后主负责人，须线下核实处理完成后填写说明手动结案。
