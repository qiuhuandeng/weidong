V3 移动端页面设计规范

版本 1.0 · 2026年10月23日 · 从原共用规范 1.44 迁入，既有规则与视觉保持不变。

本规范归档于 v3/docs/，由仓库根目录 AGENTS.md 指向。适用入口为 v3/v3.html，包含订单、工作台、客户、退款和各级内嵌移动页面。下文页面名以 V3 项目目录为基准。

项目与公共 UI 边界

  • v3.html 是当前完整运行入口，CSS、JS、内嵌资源与演示数据保留在文件内，单独复制 V3 项目即可运行，不依赖 PC 的 share/ 或中台文件。
  • 当前用户要求优先，其后按本规范与 V3 已确认实现执行。通用样式、表单控件、状态、弹层和滚动规则在 V3 公共实现中统一维护；新增页面直接复用，不复制 PC 桌面组件或中台皮肤。
  • 保持固定手机画布宽度与缩放、现有字号和间距；手机端选择、编辑和资料查看使用现有全页或手机内弹层，不改成桌面右抽屉。
  • 路由、存储键、父子草稿、取消返回、键盘和触摸行为保留。页面仅按业务改变字段与流程，公共 UI 变更须回归所有使用页面，不覆盖已有用户改动。
  • 与 PC 财务的原型联动仍使用同浏览器同源存储；仅移动目录不会改变同源。若以后分开域名部署，需要另外接入共享服务，不能声称原 localStorage 会跨域共享。
  • 不引入真实支付、转账或消息服务。新页面验收搜索、保存、取消、返回、加载失败和窄屏交互，保存截图；规范正文与阅读版一起维护。

内嵌档案与纠错流程同时遵循本项目 业务约束.md 的业务边界。

V3 门店工作台滚动规范

v3.html 的全部页面统一隐藏横向和纵向滚动条及其占位，包括门店订单、工作台、数据、会员、各级详情与表单、弹窗，以及内嵌功能页面。保持现有固定宽度，不因隐藏滚动条改变页面缩放。

通过公共滚动条样式实现隐藏；内嵌页面由统一入口注入同一份样式，后续新增页面也必须继承。保留原有滚动容器及滚轮、触摸、键盘滚动，不以 overflow: hidden 替代可滚动区域，不裁切长内容。交付前验证长页面、弹窗和内嵌页面可滚动至末尾，底部操作可访问且无滚动条。

V3 订单退款拆分

v3.html#refund 使用“填写退款 → 选择流水”两步流程。第一步先选择订单项目、填写各项目退款金额并计算订单退款合计；项目及订单剩余可退金额继续作为总上限，退款说明及项目剩余数量沿用既有规则。原型的退款凭证为选填，不上传也可进入第二步并提交，页面不显示必填星号；如已上传则随申请保留并展示。第一步校验通过后进入第二步；返回修改项目后保留流水、凭证、原因和各收款方式的草稿。

第二步按三个区域组织：第一块保留订单退款合计及修改项目入口；第二块为“可原路退款记录”，仅展示仍有可退余额、符合渠道与期限规则的原路流水，非支持渠道、超期、日期异常及余额用完的流水不展示，全选也排除。只有勾选流水时，才在该卡片底部显示“实时原路退款金额”；无可选流水时显示简短空态，不显示全选或零元原路汇总。第三块将“人工审核转帐金额”与“收款信息”放在同一卡片，不再单独展示“退款金额分配”卡片。 实时原路退款金额、人工审核转帐金额沿用 14px / 20px、500 字重；底部退款合计沿用 20px / 26px、600 字重。三处仅以橘红色 #f0643b 强调，不放大字号或额外加粗。两处卡片金额行垂直居中；顶部订单合计保持原样。流水内的可退金额降为 13px、500 字重、次级文字色，避免与汇总金额争夺重点。

实时原路退款金额 = 退款合计与所选有效流水可退金额的较小值；人工转账金额 = 退款合计减去实时原路退款金额。申请退款 500 元、选择 400 元流水时，第二块底部显示实时原路退款 400 元，第三块显示人工审核转帐金额 100 元及收款信息表单。增减流水或项目金额后即时重算；未选择流水或无可实时退流水时，按全额人工转账处理。返回重绘时清理已经不可用的流水选择，避免隐藏的失效项阻断后续操作。

人工转账金额大于零时，第三块显示“人工审核转帐金额”，收款方式提供银行卡、支付宝、微信，复用既有收款方式单选组件。银行卡必填开户姓名、银行卡号（12 至 30 位数字）及开户银行 / 支行；支付宝、微信必填收款人姓名及对应账号，不要求银行卡或开户银行，不追加账号格式的深度校验。各方式草稿独立保留，切换不改变退款金额或流水选择；确认申请、结果、退款详情与财务任务按所选方式展示和保存收款信息。全额原路退款隐藏整个人工转账区域，不展示备用收款账户选填表单；再次产生人工金额时恢复方式与草稿，后续原路失败转人工时再按需补齐收款信息。

确认申请、提交结果和申请快照显示同一份原路 / 人工拆分。仅原路部分占用所选流水额度，申请全额占用订单和项目可退额度，人工部分不得伪装为支付流水。提交时复核金额与必填信息，退款申请及各去向的财务任务一同保存，重复提交不新增任务。提交结果提示等待财务处理，不把申请成功当作退款到账，也不承诺未经渠道确认的到账时间。

V3 原型主页面统一通过本地存储适配器读写：浏览器禁用存储或空间不足时自动使用当前页面的内存数据，演示导航、退款提交、记录、重试和转人工仍可操作，不弹出存储不可用提示。尚未持久化的数据优先于旧缓存，防止演示订单已在页面中却在提交时被判定不存在；存储恢复后，下一次保存可正常写回。此兜底仅保证当前页面会话，整页刷新重新读取已持久化数据及演示样例。旧日期的演示订单链接缺少对应记录时，自动进入当天同场景的演示订单并更新地址；已有订单保持原数据，普通失效订单链接返回订单列表，不显示无法继续的“订单不存在”空页。

工作台保留“退款记录”入口：#refund-records 查看本门店记录。订单详情不再提供退款记录快捷入口，支付记录中也不再嵌入退款记录卡片；移除本单退款列表，旧链接中的订单 id 清理后进入工作台退款记录。列表以一笔退款申请为一条记录，同一申请的原路退回、人工转账分行展示各自金额和状态，不用单一总状态遮盖另一部分进度；全额原路或全额人工只显示实际存在的方式。每笔原路流水、人工余额各有独立执行任务，按明确的申请编号归组，不因客户或订单相同合并不同申请；即使本地缺少申请快照，也保留财务任务的正确归组及合计。历史申请没有执行结果时显示待处理，不伪造退款成功。 列表提供一条明确命名的“示例·原路退款成功”记录，原路退回 500 元；已有演示安装增量补齐，不覆盖原记录或重复添加。所有退款记录沿用普通白底卡片及正常文字颜色，成功记录不添加整卡灰色遮罩、灰底或文字淡化；通过绿色“已退款”状态区分成功记录，详情链接仍可点击。部分成功或仍有失败 / 待处理部分的申请继续分别显示各部分状态。

#refund-record?id=退款申请编号 顶部显示申请合计、各方式金额和状态、已退款金额；下方以连续白底分段直接展示客户、会员、订单、申请人、时间、原申请拆分、退款项目、退款说明、凭证、各笔退款明细及处理记录，不再提供“查看申请及凭证”二次入口。图片凭证直接展示缩略图，PDF 直接展示文件名和下载入口；缺失内容如实显示。退款明细列出流水、状态、失败原因、人工收款方式、对应账号及处理时间。保留原申请快照；转人工后概览按实际去向更新，已成功部分不参与重试或再次转账。从详情返回工作台退款记录列表，不再进入本单列表。

详情底部仅在有明确失败且已通过审核的原路任务时提供“重试催办”“转人工转账”两个按钮，统一处理本次申请中符合条件的失败部分。点击重试立即生成各笔独立请求编号并提示“操作成功，已重新请求扣款”；等待回执期间不允许重复重试、转人工或取消，成功才显示已退款，失败保留原因并可再次重试。重复、过期回执不得覆盖新状态，刷新保留请求及结果。转人工时检查本次申请已有的完整收款账户（包括同申请人工部分的银行卡、支付宝或微信），方式及账户信息一致时直接复用并提交；未填、信息不完整或已有账户不一致时，先选择收款方式并填写对应必填信息，切换时各方式草稿独立保留。取消填写不改变退款方式；提交前逐笔复核状态，整批保存失败不转换部分任务，不重复占用订单金额或创建退款任务。提交后进入 #refund-transfer-result 的“转人工转账成功”结果页，显示本次转人工金额和收款信息，明确“等待财务人工转账”，实际状态为待人工转账，财务确认后才完成。结果页可返回退款详情或退款记录，刷新后仍可读取已保存结果。

V3 不再提供独立的“退款补卡”入口、待办页、补卡页、提交事件或专用存储监听；旧路由不再注册。退款申请中的人工收款信息，以及保留的退款详情“转人工转账”所需收款账户填写，继续在对应流程中完成。

财务复用 pc/pc.html#refunds 的审核与提现流程。新申请按门店直提财务流程，主管 / 售后为无需审批，财务为待审核，不伪造审核人或通过时间；审核后才能确认提现、打款或确认人工转账。原型通过同浏览器、同源存储共享财务任务，PC 只导入未存在的任务，不以门店旧快照覆盖财务结果；V3 优先显示财务最新执行状态。所有记录、请求与明确命名的示例回执均仅为本地原型，不调用真实支付、转账接口；跨设备同步、支付余额和服务端并发控制需正式接入。

V3 客户列表选择控件

v3.html 客户列表的行选择与全选复用同一款圆角方形复选框：18×18px、4px 圆角、1.5px 浅灰边框（#cbd5e1）、白底；选中为公共主色蓝底白勾，部分选中为蓝底白横线。原生 input 保留复选框语义、键盘空格切换、禁用状态与 focus-visible 焦点提示；行选择点击区域保持 42px 宽，全选与行选择在同一竖线上。仅替换控件外观，不改变列表固定宽度、行高、选择逻辑或滚动能力。

移动审核端

移动审核端沿用 complaint-prototype/workflow/index.html?view=h5#/mobile 的列表、详情和全页表单交互。桌面预览保留手机外框、状态栏、顶部听筒与底部横条；框宽 404px，7px 深色边框，圆角 36px。列表卡片沿用参考页样式，审核类型切换为主要入口：三个等宽 tab，高 44px，选中项底部为 24×3px 短横线。标题栏只展示页面标题，列表页不放操作按钮。删除“共几条工单”及其整行信息。搜索和筛选固定在 tab 下方的一行内，默认直接显示，不提供展开、收起入口：搜索框高 36px、圆角 6px、浅灰底，筛选在右侧使用轻量图标加文字；搜索框内部不叠加白底或边框。筛选打开手机框内全页筛选表单；已应用条件时在同一行显示重置入口。搜索区与首张工单卡片相隔 12px。列表左右内边距 14px（小于 360px 时为 10px），卡片内边距 14px、间距 10px、圆角 12px。隐藏原生滚动条及其占位，保留触控、滚轮与键盘滚动；不显示演示审核身份或角色切换控件。列表包含合并审核、纠错审核、审核记录，支持搜索与全页筛选，整张工单卡片可点击。卡片依次展示编号与状态、两行以内标题、客户与门店、来源或风险标签与当前环节、办理人与提交时间；详细申请原因在详情中展示。筛选后提供重置入口，完整筛选表单保留重置。合并审核与纠错审核详情具体参照 complaint-prototype/workflow/index.html?view=h5#/mobile/KS20260929-001：顶部独立工单信息卡片，展示当前环节、办理人、客户及所属门店、申请内容，申请人、提交时间及附件放在更多工单信息。合并审核下方分为“方案概览、档案对比、订单方案、影响明细”四个等宽 tab，字号 13px，不显示数量；方案概览依次展示方案摘要、独立的纵向处理流程及操作记录卡片，操作记录不再单独设 tab。纠错审核固定为“方案概览、业务调整、影响核对”三个等宽 tab，执行后增加“执行结果”。处理流程后紧接独立操作记录卡片，不再单设操作记录 tab；快照、全部业务和单项资料通过手机框内全页详情查看。不提供办理时效。流程节点展示办理人、实际状态及已记录时间，不编造历史审批信息。操作记录按时间倒序展示节点操作、操作人、时间和说明。底部固定审核操作，驳回、转交、财务核对与筛选使用手机框内的独立全页表单，返回保留父级方案与列表位置；不套用 PC 右抽屉。PC 与 H5 共享已提交方案、审批结论、执行状态和完整审批链路；合并审核与纠错审核详情全部只读，审核意见在通过确认表单中填写。

合并审核详情内容

合并审核详情保持既有抽屉、手机框及卡片样式，PC 与 H5 统一按四个 tab 组织内容：方案概览展示申请信息、参与档案、主档案、订单处理摘要及处理流程，流程下方紧接独立操作记录卡片；档案对比展示身份核实依据、全部参与档案资料、主档案选择依据和证据材料；订单方案展示每笔订单的已提交处理方式、处理依据、金额及预约金、关联收退款、门店、预约 / 接待 / 客服与关键时间，进行中订单优先，历史订单随后；影响明细展示合并后资料及取值来源、客户类型、余额与流水、项目服务、客服与门店人头变化和资料缺项。概览中的操作记录按时间倒序展示申请、审核、转交、驳回和系统执行轨迹，“查看驳回原因”直接定位到该卡片。系统推荐只作参考，不将相同手机号视为已确认同一人。审核详情不显示主档案选择、订单处理下拉框、采用系统建议或方案调整说明；方案有误直接驳回，审核通过只执行已提交方案。批准前再次核对流退订单、取消预约时间及人头影响。将档案去重数与预约 / 到店人头分开，并列出受影响人员及订单；缺少独立支付流水、剩余权益核对或提成明细时明确展示资料限制。历史完成记录读取保存的结果快照，旧审批方案若有差异仅作历史追溯。

H5 订单方案使用独立的紧凑列表，突出每笔进行中订单的“保留订单 / 合并流退”结果及取消排客等直接影响。项目、来源档案、状态用于识别订单，预约时间、门店、预约及接待人员作为次级信息；金额与预约金紧凑同行展示。删除列表中的系统建议、重复的保留说明及未填写依据提示；实际处理依据、创建和支付时间、客服及资金明细进入手机框内只读“订单资料”页，返回保留订单方案位置。历史订单置后精简展示，不与进行中订单争夺重点。PC 订单表格保持原有布局和内容。

纠错审核详情内容

纠错审核详情保持现有 PC 抽屉、H5 手机框、卡片与字号间距，PC 与 H5 共享已提交或已通过的方案快照，详情全部只读，审核意见仅在通过确认表单中填写。方案有误直接驳回，不在审核端修改客户、订单、资产、资金、服务或员工分配。固定三个 tab：方案概览、业务调整、影响核对；存在实际执行结果后增加执行结果 tab。

方案概览展示申请原因、核实依据、证据、关联合并关系、当前有效档案及本次客户，明确新建一份档案、使用已有档案或仅纠正当前档案；支持多份历史参与档案。风险等级使用已提交标记与实际风险说明，缺少说明时如实提示，不推测风险规则。处理流程后展示独立操作记录卡片，查看驳回原因定位该卡片。合并前快照仅用于追溯，不能恢复已消费、已退款或已不存在的数据。

业务调整默认展示本次实际变更，按订单、项目资产、账户资金、服务扣减、回访关联记录、补录订单、身份及资料组织；未变更业务通过查看全部业务查阅。PC 使用只读表格，H5 使用紧凑列表，突出处理动作、去向及数量金额。进行中订单优先，订单人员、完整时间、关联资金权益及员工分配进入订单资料；实际变更依据保留，无依据不展示空提示。H5 二级资料使用手机框内全页页面，支持逐层返回并保留原滚动位置。

影响核对区分内部归属调整、实际收退款、档案数量、预约和到店人头。原交易保留，内部调整不新增实际收款、不再次退款；列出双方调整前后订单、余额、冻结、待补收与客户类型，核对受影响权益和扣减。人头按订单客服、门店及客户档案去重预估，标明口径与受影响订单，不将新建档案直接等同员工人头。业绩默认随关联订单或资金迁移，原员工分配保留；明确更正时列出员工、门店、原值与新值、提成、依据、调整期及历史已发。执行结果读取已保存结果与调整单，不以预估冒充实际结果。

移动档案工作台（新版）

移动档案工作台通过“档案治理 → 移动端预览”页面内的切换按钮访问，保留 #mobile-store 路由、原门店工作台、PC 页面及审核端。沿用现有 404px 手机外框、状态栏、听筒和底部横条，列表与详情复用审核端的颜色、字体和卡片规范；表单单列、控件适配触控，底部主操作固定，搜索筛选保持次要层级。所有选择、编辑、确认和资料查看均在手机框内使用全页页面，不使用 PC 右抽屉或居中弹窗。

新版提供档案合并与纠错工单两个主要入口，包含申请、记录、草稿、搜索和门店及状态筛选。合并申请分为确定主档案、处理订单、合并确认三步；支持两份、三份及更多档案，客户资料卡横向切换，不默认指定主档案，未选择主档案不能继续。进行中订单先展示，逐笔决定保留或合并流退；确认页核实姓名、手机号等资料及申请依据后提交审核。

纠错申请分为申请依据、客户档案、业务调整、提交确认四步。先关联合并记录，再明确本次客户；手工新建、引用历史资料新建、使用已有档案采用统一资料入口，姓名、手机号和新档案门店必填。业务按订单、资产、账户资金、回访服务、关联业绩、档案身份分类，逐项编辑使用独立临时数据，取消不改变方案。订单归属联动未单独修改的关联业务，允许有依据的例外；支持部分权益或资金调整、冻结核对、服务扣减纠正、原流退订单补录及必要的原计奖更正。所有提交沿用 PC 校验与单次最多一份新档案规则。

移动端与 PC 共享草稿、已提交方案、审核状态及执行结果。草稿可恢复，未保存申请离开前可保存或放弃；只填写或提交申请不会创建客户、迁移业务或生成资金调整。门店详情只读，展示处理流程、操作记录与实际结果，不显示审核通过或财务确认按钮；驳回后通过重新申请核实并提交。合并记录支持结果、订单处理、合并前快照和操作记录，冷静期无后续业务时可按既有规则撤销，符合条件时衔接发起纠错。
