# WEID微动 · PC 后台 UI 规范

版本 1.22 · 2026年10月23日 · 适用入口：PC 子项目 `pc/pc.html`

本规范位于 `pc/docs/`，由仓库根目录 `AGENTS.md` 指向。下文源码路径与构建命令以 PC 子项目根目录 `pc/` 为基准；可在仓库根目录运行 `python3 pc/share/tools/build.py`。文档链接按当前文件位置解析。

构建和完整验收按需执行，不再作为每次修改的固定步骤。默认只检查本次改动及受影响的路径，局部文案、样式调整不执行全站回归；默认不生成或保存验收截图、测试报告、临时验收脚本到仓库。仅在用户明确要求时保留这些交付物；检查结果在回复中简要说明，未执行的检查不得声称通过。本文的工具命令与验收清单均为按需参考。

确需生成截图、测试记录、报告、日志或一次性验收脚本时，使用本任务专用临时目录，查看确认后立即删除，最迟交付前清理；仓库内和临时目录均不留本次一次性产物，除非用户明确要求保留。只清理本任务产生的临时文件，不批量删除既有正式测试代码、历史资料、用户文件或页面运行资源。

## 适用范围与优先级

本规范是 `pc.html`、后续 `pc-<业务>.html` 共用的 PC 现有页面、各层弹窗与抽屉，以及后续新增页面的正式 UI 实现依据。PC 后台采用公司旧系统的视觉与公司组件库，独立于其他原型入口的 UI 标准。

唯一组件视觉基准：[公司组件文档](https://static.service.4ba.cn/by-components/)。必须对照其表单搜索、表格、通用输入、通用选择和弹窗的实际示例。旧 [公司门店列表](https://test.by4dev.4ba.cn/web/wd/manage/#/shop/shopList) 只作为壳层与业务布局补充，不能覆盖组件文档。

运行组件来源：[@weitutech/by-components-v3](https://www.npmjs.com/package/@weitutech/by-components-v3?activeTab=readme)，固定 1.1.26。文档站当前使用 Vue 2 / Element UI，原型使用公司 Vue 3 包 / Element Plus；组件名称、布局与交互按文档，版本默认尺寸差异在公共适配层统一修正。禁止把文档站的演示导航复制成业务后台，也不混装 Vue 2 / Vue 3。

优先级：当前用户明确要求 → 本规范及 `share/` 公共实现 → 本目录 [业务约束.md](./业务约束.md) 的业务约束。旧规范中的 150px 侧栏、56px 顶栏、16px 页面留白、无标签搜索、白色搜索按钮、上置标签门店表单等视觉规则不再适用于 `pc.html`。业务规则、审核边界、数据含义和草稿机制继续保留。

仓库根目录 `index.html` 只负责导航；中台与 V3 分别遵循各自项目内的规范及已确认实现，不引入 PC 的 `share/`，不参与此构建。H5 及移动预览也不因本规范变更主题。不要用 `pc.html` 覆盖任何其他入口。仅修改 PC 时，应对比导航、中台与 V3 入口的 SHA-256，确保未动其内容。

在统一 UI 规范下遵循最小改动范围：

- 普通文案、字段、数据、业务流程和现有组件参数调整，默认只改 `share/pages/<业务名>/` 内对应业务源码，优先复用已有组件、样式和变量；按现行规范修正页面实现也不顺带改公共层、无关页面、构建工具或配置。
- 公共文件仅在现有能力不足、确需新增可复用样式 / 组件，用户要求统一调整，或问题根因确在公共层且需要统一修复时修改。修改前说明原因与影响范围，按需检查受影响调用处；单页业务布局保持在所属模块，不提升为公共规则，也不通过单页覆盖破坏统一 UI。
- 读取和遵循规范不要求每次改规范。只有新增可复用样式 / 组件能力、改变通用 UI 或业务约定、修正规范错误，或用户明确要求改规则时，才更新对应规范条目和阅读版；普通页面调整、复用已有组件及沿用现行规则的公共缺陷修复，不修改规范或版本号。AGENTS.md 只在其中的约定确实变化时更新。
- 路由登记、生成入口与发布资源仅按实际依赖更新，不将最小改动机械理解为只能修改一个文件。交付前核对实际修改范围，清理本次无关改动和临时产物，保留用户及其他任务已有改动；不为留痕新增验收文件。

依赖固定为 Vue 3.5.13、Element Plus 2.9.3、公司组件库 1.1.26。公司 UMD 已包含其 VXE 依赖；不要再加载另一份 VXE、Vue 或 Element Plus。交付使用 `pc.html` 加 PC 项目内同级的 `share/dist/`，所有运行资源同源，不依赖第三方 CDN，不需要运行 npm install。旧的“PC 离线单文件”约定自本版起由此结构替代；其他系统入口不受影响。

构建按上述依赖顺序合并为一个带内容哈希的 `vendor` 脚本，公共适配器仍单独发布；厂商源码、版本与导出不变。厂商 CSS 中的内嵌字体由构建提取至 `dist/fonts/`，保留 WOFF2 / WOFF / TTF 原始字节与回退顺序，浏览器仅请求实际使用的格式。发布必须包含字体目录，不手改生成 CSS 或删除回退格式。

发布包实际 UMD 文件名是 `by-component-v3.umd.cjs`，全局导出为 `ByComponentsV3`；组件位于 `ByComponentsV3.components`，插件位于 `.default`。发布包仍含 `process.env.NODE_ENV`，构建时统一替换为 production 常量。不要在业务脚本伪造 process 全局变量。

## 新组件选用与规范补全（强制）

公司组件库是所有后续 PC 页面和新增交互的默认组件来源，范围不限于当前已经使用的搜索、表格和表单。本地规范没有写到某类组件，不代表可以自行设计另一套样式；必须查阅 [公司组件文档](https://static.service.4ba.cn/by-components/) 中对应组件的示例与说明，再核对当前项目固定版本的实际能力。按业务需要接入组件，不要求页面使用组件库的全部组件。

### 查找与采用顺序

1. **先查本地规范与公共封装。** 已有同类组件时直接复用 `share/js/components.js` 与 `share/css/theme.css`；业务字段、数据和事件由页面提供。已确认的 13px 字号、28px 搜索控件、固定宽度、44px 页签及抽屉规格继续有效，不因查询官网示例而恢复其默认大尺寸。
2. **本地未覆盖时查公司文档。** 查找对应的用途、示例、属性、事件、插槽、禁用 / 空态 / 加载态和交互行为；记录实际查到的文档地址及查阅日期。不能只看截图、组件名称或凭记忆猜 API，也不能将文档站的演示导航、业务数据或操作要求直接当作项目需求。
3. **核对项目版本后接入。** 检查 `vendor/manifest.json` 的版本以及 `ByComponentsV3.components` 的真实导出，结合本地包实现核对 API。文档站与 Vue 3 包存在版本差异，文档上有的组件不一定在当前包中可用。包已提供的合适组件优先真实挂载；尚无公共封装时，先在公共适配层封装并统一主题，再供业务页使用。
4. **缺少组件时采用统一兼容方案。** 当前公司包未提供对应能力时，先考虑组合已有公司组件，再选择项目已安装的同一版本 Element Plus 基础组件；两者都不能满足时才封装业务专用组件，并继承公共主题、尺寸和交互机制。兼容方案必须说明缺失原因、实际基础组件及维护位置，不得伪称已使用不存在的公司组件，不通过引入第二套 UI 库或 CDN 解决。
5. **新增公共能力后补全规范和目录。** 仅在本次新增公共组件封装或通用能力时，将适用场景、实际组件、默认参数、尺寸 / 状态 / 交互、公共入口、参考文档及验证页面写回本规范与下方选型目录，生成 HTML 阅读版。页面首次使用已接入的组件仍属于复用，不改公共封装或规范；不得每个页面再各做一份。

文档查询不意味着自动升级依赖。本项目继续固定当前版本；若业务确实需要升级，需明确兼容影响并按依赖升级要求更新包、哈希、构建产物与回归记录。文档站无法访问时，先使用本地已验证的规范、封装、固定版本源码及已有参考记录；缺少 API 证据的组件不标记为“已验证”，可采用已验证的公共兼容方案，并在交付记录说明待核对项。不得静默猜测用法或宣称已对照当前在线文档。

## 默认紧凑密度

按用户 2026年10月22日的反馈，`pc.html` 全部现有页面与后续新增页面默认采用紧凑密度。公司组件、颜色、结构与交互继续沿用，官网演示的普通大尺寸不直接作为原型默认值。统一使用下表中的字号、控件、行距和间距；不通过浏览器缩放、CSS zoom 或 transform 缩小整页，也不只给单个业务追加密度样式。

密度变量集中在 `share/css/tokens.css` 的 `--pc-font`、`--pc-control`、`--pc-search-control`、`--pc-table-line`、`--pc-table-padding`、`--pc-form-gap` 和 `--pc-gap`。组件适配层选择对应的 small / default 尺寸；不得恢复 large 表单或 14px 大列表作为默认。

紧凑控件与搜索区留白分别管理。搜索区使用 `--pc-search-padding`、`--pc-search-row-gap`、`--pc-search-actions-gap`、固定字段宽度 `--pc-search-field-width:280px` 和公共 ByForm 的 24px gutter；禁止为压低整块搜索区而取消条件行距或挤压按钮行。

## 列表与搜索

有业务 tab 时执行上方“全页面统一 Tab”，紧邻搜索区域。搜索与表格内容分为两块白底区域，间隔 12px。页面顶部、左右边距与该间距一致，均使用 `--pc-gap:12px`；首屏 critical CSS 与完整主题保持相同规格。旧兼容 CSS 不再以 `!important` 固定搜索区下方 16px；内容 tab 与搜索区仍为零间隔。

搜索条件采用公司后台的横向标签：标签在控件左侧，以“：”结束，不在控件上方加标题。标签应描述条件本身，例如“状态”“城市”“申请日期”，不要写成程序变量名或重复“全部”。搜索使用真正的 ByForm：设置 `labelWidth: auto`，由当前搜索区最长标签统一决定该搜索区的标签列宽；标签 13px 字号、32px 行高、右侧间距 8px、单行显示。短标签页面不再统一预留 120px，例如门店床位的标签列宽为 60px（含右侧间距）；不得给所有搜索区强加过宽标签列，也不得让各字段分别自定标签宽度。内部输入和下拉保持 28px / 12px 的 mini 视觉尺寸。

普通搜索控件区域固定为 **280px**，由公共变量 `--pc-search-field-width` 管理；输入、下拉、单日期、选择按钮和组合关键词均遵循此宽度。日期范围及展开式状态选项组按下方专用宽度规则执行，不能机械套用 280px 导致选项折行。每项总宽为本搜索区统一标签宽 + 当前控件固定宽度，项间保留 24px。按业务顺序从左向右排布，空间不足时整项换行；不再采用百分比均分或固定三 / 两 / 一列断点。宽屏自然容纳更多条件，剩余空间留在行末，不能靠放大控件填满。主页面与各层抽屉都按自身可用宽度自然换行；只有单项仍放不下的极窄容器，才允许普通输入收缩防溢出，展开选项组则切换为下拉。

**对齐是公共组件的强制要求，不只检查间距。** 同规格条件的标签与控件边界保持一致，同一行的第一排控件顶部对齐。日期组合及宽档状态组完整占用自身宽度，不挤压相邻输入或强行与 280px 控件对齐右边界。组件不随页面宽度伸展；内部允许填满自己的固定容器，禁止直接按页面或百分比栅格设置 100% 宽。清除旧页面 160px / 240px 等冲突宽度及 max-width。选择按钮的文字靠左、箭头靠右；组合关键词整体 280px，类型选择器 112px、间隔 8px、输入框 160px。ByForm 本身采用占满容器的块布局，不继承原搜索 form 上的旧 grid / flex 排版。

所有页面及各层抽屉的搜索区统一执行以下间距，不随表格紧凑密度压缩：

| 搜索区项目 | 固定规则 |
| --- | --- |
| 条件控件宽度 | 普通控件与组合关键词固定 280px；双日期范围 320px；带快捷项的日期组合 520px；展开状态组按 280 / 320 / 400 / 480 / 560 / 640px 档位；均不随页面拉伸 |
| 标签列宽 | ByForm `labelWidth: auto`，以本搜索区最长标签为准；右侧留 8px，不统一空出 120px |
| 外围内边距 | 上下 16px、左右 20px；视口不超过 760px 时四周 12px |
| 条件行之间 | ByForm 的行容器设置 row-gap:12px；普通条件行高 32px，相邻行起点间隔 44px，28px 控件间实际留白约 16px |
| 条件列之间 | ByForm rowAttrs.gutter=24；标签与所属控件之间仍为 8px，不给单个字段另加随机 margin |
| 按钮行 | 条件区下方独立一行，距离最后一行内容 16px；按钮之间 8px |
| 日期快捷项 | 紧跟所属起止日期右侧，间隔 12px；快捷项之间 12px，高 28px，与日期控件垂直居中，同组永不拆行。搜索容器不超过 620px 时收进同一行的“快捷日期”菜单，所有原快捷项及事件保留 |
| 其他附加条件 | 独立行，与上方条件区相隔 12px；之后到按钮行仍保留 16px |
| 换行与自适应 | 空间不足时条件整项换行，下一行继续保留 12px；日期组合与展开状态组内部不折行；搜索容器不设固定高度，不用负边距压缩内容 |

ByForm 使用公共固定宽度条件项和自动换行布局，禁止恢复百分比列宽、flex-grow 拉伸或业务专用断点。双日期区间由公共适配器标记 `pc-query-range`，完整区间固定 320px；组内使用 `minmax(0,1fr) auto minmax(0,1fr)`，起止日期等宽，中间保留“至”和两侧 8px 间距。带快捷项时整组固定 520px，范围本身仍为 320px，快捷项在其右侧；普通字段不得跟随加宽。日期输入高 28px、条件行高 32px，不靠增加高度容纳换行。搜索容器不超过 620px 时整组使用 408px（320px 日期 + 12px 间隔 + 76px 快捷菜单），极窄容器内等比收缩两个日期框，仍保留两个日期和同一行菜单，不溢出页面。必须保留两个独立日期控件、原字段及事件，不能在移除旧 label 文案时丢失结束日期。禁止逐页另写宽度、给日期保留双列空位或缩小字号强塞更多条件。

条件行距由公共行容器统一提供，字段自身不叠加下边距；最后一行到按钮行只计算一次 16px。新增或修改页面必须复用公共搜索适配器，不得将 row-gap 清零、把紧凑控件高度当作整行间距，或仅修补一个业务页面。

按钮放在条件下方的独立行并靠左，顺序为“重置”“搜索”，高度 28px、最小宽 68px。重置是白底线框，搜索是蓝色主按钮，带公共搜索图标。输入框按 Enter 执行同一个搜索动作；搜索重置回第一页，重置恢复本模块默认条件。抽屉内搜索只改变该层结果。日期快捷项不添加“关键词”等无关标签。

少量状态选项使用 ByCommonSelector 的 border 模式展开，选中项显示蓝色边框；长列表使用 select 模式。展开组选项字号 12px、高度 28px、间距 6px，保留键盘和单选语义，不自绘胶囊按钮。选中、悬停、焦点切换均不改变控件位置、高度或组宽；禁止沿用选项 hover 上移动效。公共主题覆盖厂商单行组的 `overflow:hidden`，并将隐藏的原生 radio 定位在选项内部，防止点击或键盘聚焦触发内部纵向滚动；不得靠点击后重设滚动位置或负边距补偿。**选项组内部必须完整保持一行**，禁止把“已拒绝”“退款异常”“冷静期中”等挤到第二行、截断或隐藏。

公共适配器按整组选项的实测宽度（含选项间距和 8px 字重余量），从 **280 / 320 / 400 / 480 / 560 / 640px** 选择能容纳内容的最小固定档位。退款审核组通常使用 320px，客户合并状态组通常使用 400px；普通输入和下拉仍为 280px。档位由内容决定，不按剩余页面空间任意拉伸；当前行放不下时整组进入下一行。若连单独一行也放不下该组，或内容超过最大档位，则自动使用同一 ByCommonSelector 的 280px 下拉模式，保留选中值与事件；容器变宽后恢复展开，不产生内部换行或溢出。

列表标题保留业务必要名称。新增、导出、批量操作使用同一工具栏；门店列表按旧系统排列新增、转出及日志操作。行操作在最右列，统一蓝色文字按钮。禁用动作应有真实 disabled 状态，不能只改颜色。

## 表单与基础控件

普通门店 / 规则配置字段及夹在说明、条件组、表格之间的独立字段均使用公司 `ByForm` 的 custom slot 承接现有业务字段，底层为 Element Plus Form。标签右对齐，默认宽 110px，控件高 32px，标签字号 13px。短字段双列、列间距 16px，长文本通栏，行间距 14px；简单窄抽屉使用单列；多行文本域最小高度 64px，按内容增高。

输入框和文本域使用公司 ByCommonInput，下拉 / 展开枚举使用公司 ByCommonSelector；底层继承 Element Plus。日期、时间、开关使用 ElDatePicker、ElTimePicker、ElSwitch；配置表单复选框使用 ElCheckbox，按钮使用 ElButton。日期值保持 YYYY-MM-DD，时间值保持 HH:mm，提交前后不转换业务时区。表格批量勾选、选择抽屉及配置单选同样使用 ElCheckbox / ElRadio，保留原字段、互斥分组及事件；月份使用 ElDatePicker 的 month 模式和 YYYY-MM 值。日历保留专用结构，但其中的基础选择控件不豁免组件接入。不得新增原生控件皮肤，新 Vue 表单直接使用 ElCheckbox / ElRadioGroup。隐藏兼容字段不算可见 UI 组件。

必填红星、横向标签、placeholder 和 aria-label 一并保留；缺失只读信息显示“—”。标签应关联真实可交互控件。隐藏原生字段仅用于兼容现有 ID、FormData 和事件读取，不可成为可聚焦或重复朗读的控件。

公司组件的默认校验不代替业务校验。保留原来的必填、范围、审核条件、只读及禁用逻辑；不要为视觉统一加新的隐藏门槛。保存成功才写入当前业务数据；取消不提交当前层草稿。

## 提现管理与原路退款失败处理

`pc.html#refunds` 下新增“提现管理”，与退款管理、退款列表、退款明细并列。提现管理负责财务执行，退款列表保持原有查询字段及行为；属于提现任务的记录不能从旧列表的批量完成入口跳过门店补卡和提现流程。各 tab 的搜索、页码、选择独立；提现管理默认本月，旧 tab 保留原示例日期范围。

退款与提现的确认弹层、操作反馈不添加“当前为本地示例”“不发起真实退款”等原型实现说明，也不追加“（示例）”后缀；仅保留业务操作所需的提示。离线原型的数据及支付边界记录在规范和验收文档中。

- 搜索含申请 / 确认 / 提现日期及快捷日期、提现状态、退款类型、退款状态、退款方式、客户 / 申请人 / 关联单号 / 会员号 / 退款单号关键词。复用 ByForm、ByCommonInput、ByCommonSelector 和公共日期组件；状态组选项保持一行，按公共档位及下拉回退规则适配。
- 提现列表复用 ByTable / ByPager，首屏突出客户、退款金额、退款方式、提现状态、退款状态和失败原因 / 处理提示；保留会员号、退款类型、原始支付方式、确认 / 提现 / 审核时间、申请人、关联单号、退款说明等字段。退款方式为“原路退款 / 人工转账”，不与银盛、支付宝等原始支付方式混用。操作固定在最右列，细节进入 1120px 共享详情抽屉。
- V3 订单退款提交后，按每笔原路流水和人工余额分别导入财务任务，关联同一申请及订单；主管 / 售后为无需审批，财务为待审核，审核通过后才能确认提现。仅导入未存在的任务，重试、补卡和财务处理结果以已存在的财务记录为准，不由门店旧快照覆盖。退款详情复用现有公共信息、项目、审核与操作记录，展示原支付流水编号。
- 门店退款记录允许对已审核且明确失败的原路任务自行重试或转人工；已有完整收款信息时确认复用，缺失时先选择银行卡、支付宝或微信并填写对应收款信息再提交，状态进入待人工转账。沿用同一任务编号、金额和请求历史，成功的其他去向不重复退款。PC 财务页已删除“重试退款”和“要求转账”的列表 / 详情入口、确认弹窗及提交逻辑；原路失败只展示失败原因及等待门店处理的提示，无可用操作时不显示空的“提现处理”分组。
- 提现状态与退款状态分开存储：待确认 / 待提现 / 已提现 / 已取消；退款状态为审核中 / 处理中 / 已退款 / 退款异常 / 已取消；门店新提交任务先进入审核中。细分执行状态记录原路退款失败、等待渠道回执、待门店补卡和待人工转账，列表用处理提示说明下一步。
- 已发起的原路退款继续等待渠道回执，正常单笔 / 批量打款及其回执处理保留。成功才登记已退款 / 已提现，失败保留原因；重复、过期回执不重复推进状态。PC 不再发起失败重试或要求转账。
- 历史转账原因、补卡信息和原路重试记录继续只读展示，不因删除操作而清空。门店自主转人工及收款信息提交继续按 V3 既有退款记录流程执行；财务核对完整收款信息并完成实际转账后确认。银行卡要求开户姓名、银行卡号及开户银行，支付宝 / 微信要求收款人及对应账号；详情按方式显示字段，确认弹窗复用 ByDialog / ByTable，含六列收款信息时使用公共 wide 规格 1120px（窄屏按公共弹窗规则收缩），表格使用“收款方式、收款人、收款账号、开户银行”，非银行卡的开户银行显示“—”。历史未标记方式的账户按银行卡兼容，收款方式不改变原路支付渠道和审批状态。
- 工具栏提供批量人工转账、批量打款、撤销流退、导出。无选择或混入不符合状态的记录时禁用；批量打款只接收待原路打款记录，批量人工转账要求门店已提交所选方式的完整收款信息。撤销只允许尚未发起打款的申请，取消未完成补卡待办，不恢复原订单历史。所有确认均用 ByDialog，取消不写数据。
- 数据写入前重新读取并校验当前状态；持久化失败不推进状态。保存请求、回执、要求转账、门店提交、财务确认及撤销的时间、人员与操作记录。示例初始化只补齐明确命名的样例，不覆盖用户已有记录；内置余额不足重试成功、账户受限重试失败、待补卡、待人工转账、待确认和待原路打款场景。
- 当前为离线原型，原路请求使用明确的示例回执，不调用真实支付接口、不自动发门店消息。PC 与门店补卡使用同一浏览器及同源 localStorage 共享待办；正式权限、服务端支付接口、跨设备消息与并发控制需由服务端接入。

## 表单兼容与层级覆盖

- ByForm 是唯一真实 form。替换旧搜索 form 时，原 id、onsubmit、oninput、onchange 等事件全部迁到生成的 form，不能留在外层 div；FormData 的参数必须是 HTMLFormElement，不生成嵌套 form。
- 搜索条件分组必须展开成独立固定宽度条件项；日期快捷项挂在所属日期范围字段内，不得被识别成搜索按钮行。始终优先使用 query-actions 作为操作行。日历日期区间按公共日期规则使用 320px（含快捷项时 520px），关键词、大区、区域、门店的控件区域固定 280px，整项自然换行，不按页面宽度伸展。
- 标题、说明和规则树之间的连续 field 分组单独挂载 ByForm，保持业务块顺序，不能因为父容器混有其他元素而跳过字段转换。
- 业务采集器仅读取 input[name]、select[name]、textarea[name]，跳过兼容前缀及未选中的 radio；不要遍历所有 [name]，公司表格的列节点也可能带 name 属性。组件内部的 UI 分组字段不写入业务模型。
- 公司 ByTable 的后代 span 样式不能压扁 ElCheckbox / ElRadio 指示器；公共主题显式保持 14px 方框 / 圆点及 inline-block 显示。不能只核对组件类名，必须查看真实外形。
- 可见基础控件必须是组件实例。隐藏的原字段只负责原有 ID、数值和事件同步；单选互斥、勾选、筛选即时草稿、Enter、分页及取消都要实测。
- 通用改动覆盖主页面、页签、二级 / 三级抽屉、居中确认、历史 / 资料预览和动态新增行；日期日历、规则树等专用布局仅保留业务结构，不作为跳过内部基础组件的理由。

## 投诉处理迁移与后续维护

入口为 `pc.html#complaints`，导航为“统一客诉 → 投诉处理”。功能来源是原 index（现 `zhongtai/zhongtai.html`）内嵌的 `unified-complaints/app.js`；只迁移业务字段、数据及交互，不引入源页面样式、iframe、导航或远程运行依赖。模块在 `share/pages/complaints/business.js` 维护，专用信息结构在 `share/pages/complaints/style.css` 维护，由 build.py 构建为独立资源，仅进入投诉路由时加载。后续新增功能仍先用公共组件，不在业务文件另建控件主题。

- 保留客户小程序、移动工作台、微信支付三个渠道；列表四个状态 Tab 无数量，基础 / 更多筛选、Enter、重置、CSV 导出和独立分页均使用公共组件。收起高级筛选保留草稿及已应用条件；二级订单搜索、日期快捷项和分页不得改父列表条件。
- 列表前三列固定为“客户信息、门店 / 关联订单、投诉渠道”，随后展示投诉内容；投诉渠道列不展示内部工单号（详情中的工单号保留）。投诉内容为普通正文，不使用蓝色链接或点击入口，详情通过最右侧“详情”操作进入。此列表表头与所有单元格统一左对齐，通过公共表格 `data-pc-align="left"` 声明，不修改其他模块的默认对齐。
- 详情、处理、关联订单选择和订单资料采用 860px 公共右抽屉；回复与跟进采用 560px。层级位于 `#mergeDrawers`，复用公共遮罩、进出场、背景 inert 和关闭焦点，未保存草稿继续拦截。开始处理与结案确认用 `PCUI.confirm` / ByDialog；弹窗或组件下拉打开时，Esc 优先关闭该层，不能同时关闭后方抽屉。
- 客户反馈和关联订单放在 Tab 上方；处理中的反馈字段完整展示。关联订单按需展开，使用两行摘要及公司项目表；详情有“处理方案 / 跟进记录”，处理有“责任认定 / 解决方案”，全部沿用 44px 公共 Tab。切换保留公共信息、展开状态和草稿。
- 待处理工单点击“处理”先弹出“确认开始处理客诉吗”；取消不改变记录，确定后立即转为“处理中”并记录开始时间与操作人，按钮变为“填写处理方案”。开始处理不创建或提交方案，关闭后刷新仍保留处理中；方案单独填写与提交，首次方案不能误记为修改方案。未保存处理方案时不显示“结案”；开始处理、回复和普通跟进不算已填写方案。有效处理结果且存在方案保存时间或处理记录后，处理中工单才显示结案入口；确认及实际写入复用同一资格判断，不能仅在 UI 隐藏。
- 责任认定依次填写“责任部门 → 售后类型 → 责任人”：未选部门时禁用售后类型，未选类型时禁用责任人；闭店类型隐藏责任人字段、免除必填，保存时清空旧责任人，取消仍保留原记录。责任部门与责任人使用公司多选组件，责任人可按姓名搜索在职、离职及当前 / 历史记录中的姓名，不得只返回在职人员或丢失已选姓名。原型名册状态为演示数据，离职姓名加“（离职）”标识但不可禁用，历史状态未知时不虚构在职状态；将来接人员接口时同样必须支持离职与历史回显。
- “填写处理方案”抽屉不设置“投诉门店”编辑字段；公共订单摘要及详情中的门店信息继续只读展示，不因此改写历史门店。4 级显示必填风险类型；投诉时间为公司同版本日期时间组件。长字段可以在上下文明确时简写标签，例如“第一联系人”，不能压缩公共标签列或让单行标签挤出控件行。
- 方案只包含可组合的退款、赔偿、商品置换。退款直接带入客诉关联订单，不二次选单、不补造退款门店或业绩人员。在同一张 ByTable 内按订单标题分组，共用表头、表头全选和底部汇总；金额以分计算，校验项目、订单剩余额度及其他客诉占用，编辑自身方案不重复占用。置换商品价值独立展示，不计入退款与赔偿应付款。切换方式保留草稿，但只提交当前选中方式的字段。
- “回复客户”固定在投诉详情抽屉底部左侧，使用真实布局容器承载，不在 display:contents 的组件挂载节点上设置自动外边距。“写跟进”放在“跟进记录”Tab 内容区顶部右侧，不放在公共底栏，也不显示在处理方案 Tab。已结案（数据状态“已完成”）仍可在该 Tab 下“写跟进”，保存跟进不重开工单，不改变结案时间、责任认定或解决方案；已结案仍不可修改处理方案。开始处理事件为只读历史，不混入可编辑跟进。
- 详情、处理记录回显完整方案；保留跟进新增 / 本人记录编辑、回复文本 / 图片、结案、原始附件预览与下载。处理附件沿用 4 个 / 每个 5MB 的类型校验；回复和跟进图片沿用 4 张 / 每张 5MB。所有保存、退款与回复为本地原型行为，不调用真实支付或客户消息接口。
- 本地记录使用 `weid.pc.complaints.v1`。首次不存在该键时可读取同源原入口的 `weidong.unified-complaints.v1`，之后只保存 PC 键；两套入口后续记录独立，绝不回写 index 数据或修改其文件。不同文件来源 / 域名的 localStorage 不承诺自动同步。
- 源页面的客户 / 订单链接只有跳转提示；PC 提供当前投诉模块已有数据的只读资料抽屉。不得把这些客户强行关联到另一业务模块的同名演示客户。

## 公共适配补充约定

- ByCommonSelector 的 `multiple` 输入与输出为数组。隐藏原 select 的 selectedOptions 与可见组件同步；联动改变 disabled、选项文案或值后调用 `PCUI.syncControl(nativeSelect)`。校验定位用 `PCUI.focusControl`，不能把焦点留在隐藏的兼容字段上。
- 编辑外层用 div / section 包含字段，ByForm 生成唯一真实 form；混合分组通过 `data-pc-columns="2"` 延用两列布局，完整宽度字段使用 ub-span，560px 表单使用单列。混合表单的公共 pc-field-group 必须跨满外层网格，再由 ByForm 分列，禁止内外重复均分导致控件过窄。公共适配保留字段 data-field 和 hidden，动态显示 / 隐藏须作用到整项标签与控件。
- 公共搜索支持 `data-pc-label` 指定组合字段名；搜索按钮在独立按钮行时用 `form="搜索表单ID"` 关联 ByForm 的真实 form，确保点击和 Enter 都走同一提交逻辑。
- 独立业务分页用 `PCUI.registerPager(action, callback)` 注册，data-pc-pager 传入 total / page / size / action 及业务 scope；禁止跨模块修改 UB 状态凑用分页。
- ByTable 的单元格业务 data-* / aria-* 透传到 pc-cell，金额小计等更新定位仍有效。业务列最低可读宽度通过 th 的 data-pc-min-width 声明，窄屏只在表格内横向滚动，不把长内容列压成过窄竖列。多行信息使用公共 pc-block，多行文字操作用 pc-multiline；不能依赖厂商 span 默认显示，也不能让固定按钮高度压住多行文本。空表保留业务提供的空态文案。表格可用 `data-pc-align="left|center|right"` 指定表头与内容对齐，未声明继续默认居中，不允许用单页强制 CSS 覆盖对齐。
- 少量明细行的抽屉表格可在原始 `table` 上声明 `data-pc-min-height="0"`，由 `PCUI` 表格适配器传入已接入的 `ByTable.gridOptions.minHeight`，随内容收缩，避免单行下方留出空白；退款项目与商品置换抽屉已使用。默认最小高度仍为 160px，未声明的表格保持原尺寸；不通过业务 CSS 改写厂商表格高度。
- `PCUI` 表格适配器支持显式通栏行：`tbody > tr[data-pc-full-row]` 内仅放一个 `td`，其 `colspan` 等于列数。适配器将其转换为固定版本 ByTable 的 `gridOptions.mergeCells`，用于订单分组和表内汇总；普通行不变，未标记的任意跨行 / 跨列表格仍不自动转换。已核对 1.1.26 包的实际支持，不使用 Element UI 的表格合并 API。
- 表头全选复选框可用 `data-pc-indeterminate="true"` 声明部分选中，公共适配器透传到同版本 `ElCheckbox.indeterminate`；勾选变化后重绘时重新计算该值，不手绘半选图标。
- 自动挂载按钮、输入时保留当前焦点；业务重绘后校验、关闭与键盘 Tab 的焦点不能落到不可见原字段。

本模块功能与组件验收见 [complaints-migration.md](../share/verification/complaints-migration.md)，金额与状态回归运行 `node share/verification/complaints-business.test.cjs`。

## 新增与修改页面的做法

1. 先读取本规范及同目录 `业务约束.md` 中对应业务规则，按“新组件选用与规范补全”将本次页面及各层交互映射到选型目录；本地缺项必须查公司文档并核对固定版本，不能直接自建样式。
2. 找到当前路由对应的 `share/pages/<业务名>/` 源码，在该业务文件中调整字段、数据与动作；搜索复用 queryModule（自动挂载公司 ByForm 和控件），列表复用 table / tableHTML / list，表单复用 field 与 ub-form / rule-config-form，抽屉复用既有壳层。沿用已有能力时不修改公共实现。
3. PCUI 自动把公共结构转为真实公司组件，不只是赋予公司类名。当前 v3 包没有导出 ByPageSearch，因此搜索公共适配器用 ByForm + 同款独立操作行组合，不在各业务页分别模拟。新 Vue 功能可通过 `PCUI.mount(host, component)` 挂载，注册固定版本的 Element Plus 与 ByComponentsV3。
4. 动态重绘必须进入 #main、#mergeDrawers 或 #modal 范围，由公共观察器接管。移除宿主时自动卸载 Vue 实例，防止重复事件与浮层残留。
5. 确需新增可复用能力时，共享组件在 components.js 实现、通用视觉规则在 theme.css 实现；单页独有的业务结构样式在所属模块内维护，复用现有公共规格。新增 Vue 宿主需与既有自动适配器明确边界，避免其内部控件再次挂载，动态移除时沿用公共卸载机制。不得复制厂商组件、整页、导航或给单页叠加高优先级 CSS。业务专属合并单元格 / 日历使用明确的结构，不借例外创建另一套主题。
6. 按本次影响范围选择必要检查，构建仅在需要更新生成入口或发布资源时按需执行；仅新增公共组件能力或变更通用约定时同步对应规范条目及阅读版，普通页面改动不改规范。验证结果在回复中说明，临时截图和测试记录用完即删，不默认生成验收文件。禁止手工编辑 pc.html 或 share/dist/ 生成物，下一次构建会覆盖入口引用；应修改对应源码。

## PC 模块结构与加载性能（后续页面强制沿用）

用户要求后续新增页面继续保持快速加载。`pc.html` 仅负责入口、首屏壳层及资源清单，保留原 hash 链接与同源存储键；不按页面复制公司库，也不把业务重新拼回入口。页面可共用一个入口，下载范围以当前业务模块为界。

### 目录与模块边界

本轮目录调整必须保持已有页面的功能、业务数据与 UI 视觉。原 `pc-ui/` 源码与 `pc-assets/` 发布资源统一收进 `share/`；不要在旧位置继续维护第二套文件。

```text

pc-<业务>.html                  可选独立 PC 入口（注册后生成）
share/                          仅供 PC 子项目共用
    css/
      tokens.css                颜色、字号、尺寸、间距等设计变量

      critical.css              首屏壳层和加载反馈
      legacy-business.css       现有业务结构兼容，不继续堆新页面
    js/
      components.js             公司组件公共适配层
      core.js                   共享工具与壳层
      loader.js                 路由、按需加载和生命周期

      customer/index.js         现有档案 / 合并 / 纠错业务

```

“全局”仅指 PC 系统内全部页面：一个或多个 PC HTML 入口都通过同一模板、同一组件适配器和同一主题构建。`index.html`、`zhongtai.html`、`v3.html` 不引入这些资源；中台与 V3 分别位于同级 `zhongtai/`、`v3/` 子项目，各自维护自己的入口、资源和规范。


- `templates/entry.html` 是所有 PC 入口的唯一壳层模板；`css/critical.css` 与 `css/tokens.css` 提供首屏加载反馈，完整主题就绪后保持相同视觉。
- `js/core.js` / `js/loader.js` 只处理共享工具、导航、加载去重与生命周期；只预取当前模块和公共资源。
- `pages/customer/index.js` 与 `pages/management/index.js` 保留原互相关联的业务与草稿，不在目录迁移时重写。独立新业务必须新建 `pages/<业务名>/`，不能继续塞进这两个兼容文件。
- 模块用闭包封装状态，经 `window.PCModules[模块名]` 暴露 `render()`、可选 `redraw()` 与 `leave()`。离开时释放自己的监听、定时器、请求和弹层；不能复制导航、另绑 hashchange 或增加业务全局变量。
- `routes.json` 只登记本模块目录的 JS / CSS；构建拒绝跨模块引用、打包 vendor、重复路由与超过预算的模块。跨业务能力先放公共层，再由页面使用。
- 模块默认 `requiresUI: true`，所有表单、列表与交互控件继续加载真实公司组件。仅完全不含公司控件的静态壳层页面（当前为欢迎首页）可显式登记 `requiresUI: false`，只加载公共壳层样式与本模块；首次进入业务再加载公司库。不得以此开关绕过组件规范或自绘控件。快速切回首页不等待正在下载的业务依赖。
- 公共加载器固定样式顺序为业务基础 → 厂商组件 → 公共主题 → 模块结构样式；首次直达、欢迎页进入业务及失败重试都保持该顺序，不能让网络先后或首次访问页面决定层叠结果。回归须比较直接进入业务与从欢迎页进入时的控件布局。
- 专用 `style.css` 仅处理日历、业务信息排列等独有布局，选择器限于 `.pc-page-<业务名>` 等自身容器，注册后才随模块加载。不得覆盖 `:root`、body、通用按钮、`.pc-*` 公共控件、`.el-*` 或 `.vxe-*` 皮肤；不得用 `!important` 绕过公共规格。现有投诉结构类沿用 `uc-*`。
- `css/legacy-business.css` 是旧业务兼容文件，处于低优先级 `pc-business` layer。目录迁移不拆散其相互依赖的规则；新增业务不得继续向这里追加样式。

### 哪些规则全局管理

| 内容 | 维护位置 | 页面可以提供什么 |
| --- | --- | --- |
| 主色、文本色、字号、控件高、搜索宽、间距、页签规格 | `css/tokens.css`，原变量名和数值保留 | 使用变量，不重定义尺寸和主题 |
| 搜索、表单、输入、下拉、表格、分页、按钮、状态、弹窗 | `js/components.js` + `css/theme.css` | 字段、选项、列、校验、事件和数据 |
| 侧栏、顶栏、路由、加载与错误处理 | 入口模板 + `js/core.js` / `js/loader.js` | 导航名称、图标、路由 |
| 业务状态、搜索条件、分页、父子草稿 | `pages/<业务名>/index.js` | 独立维护，不污染其他业务 |
| 特有业务布局 | `pages/<业务名>/style.css`，可选 | 仅自身容器的结构；普通列表无需私有 CSS |

共享变量和组件规则是后续页面的默认值；“复制一页再修样式”不能作为新增方式。通用需求只改公共层并回归使用页面。公司库未封装的新控件仍执行前文选型流程，不因已有模板而跳过真实组件接入。设计变量使用标准 [CSS 自定义属性](https://developer.mozilla.org/en-US/docs/Web/CSS/Guides/Cascading_variables/Using_custom_properties)；只在 PC 文档加载，不传播至其他系统。

### 缓存与发布

构建使用内容 SHA-256 命名资源。只修改某个业务模块时，它的文件名变化；公共组件和其他业务文件名保持不变。`share/dist/` 可长期缓存，HTML 每次校验更新；不添加随机时间戳清缓存，不依赖浏览器停用缓存，也不引入 Service Worker 接管其他系统。

发布仍可通过 Git 提交，由托管平台部署整个仓库。按用户确认，仓库根目录增加 `vercel.json`，仅对 `/pc/share/dist/(.*)` 设置 `public, max-age=31536000, immutable`；HTML 不使用该长期缓存规则，继续校验更新。新内容生成新文件名，部署后浏览器会获取新资源。配置依据 [Vercel 响应头配置](https://vercel.com/docs/project-configuration/vercel-json#headers)；本地新增文件不代表线上已生效，部署后须核对响应头。

PC 的 HTML 引用 `share/dist/` 相对路径，能位于网站 `/pc/` 子目录，也能单独部署 `pc/` 为站点根目录。当前根配置按完整仓库部署编写；若单独部署 PC，须在实际部署根目录配置对应的 `/share/dist/(.*)` 路径，不能仅把配置放入任意子文件夹就认为平台会读取。中台、V3 与根导航不受这条 PC 缓存规则影响。

整站发布时保留 `index.html` 和三个完整子项目目录；PC 最小运行包是 `pc.html` 加同级 `share/dist/`，其余源码、工具和文档保留在本地维护。构建保留旧哈希资产；已发布或仍被入口引用的资源继续保留，本地未发布且未被当前入口或资源清单引用的中间产物可清理。`share/asset-manifest.json` 记录当前文件及体积。现在的正式 URL 是 `/pc/pc.html`，原根目录 `/pc.html` 不再保留实体入口；若需要兼容旧收藏地址，需在托管平台配置到新地址的跳转。

### 性能门槛与新增验收

- 构建会拒绝：入口超过 16,000 字节、共用资源 gzip 总量超过 1,500,000 字节、任何入口首次所需 gzip 总量超过 1,700,000 字节；新增独立模块（JS＋CSS）默认不超过 60,000 字节。现有客户兼容模块按迁移实测设为 180,000 字节，投诉模块为 40,000 字节；不能把这个例外用在新模块。
- 超限应拆出非首屏功能、图片或数据，不能直接调高预算绕过检查。不要重复打包 Vue / Element Plus / 公司组件库；保持固定版本及厂商校验。
- 新增页面必须记录：冷缓存首开、普通刷新、第一次进入模块、第二次进入模块。相同环境使用 4 Mbps / 80 ms 作为固定对照条件，记录首屏出现与页面可操作两个时间，不能只用 HTML 体积宣称提速。
- 验证新模块没有增加其他入口的请求；打开一个页面不会提前加载新模块；重复进入没有重复脚本与事件绑定。检查缓存复用、深链接刷新、前进后退、快速切换、资源失败后恢复，以及保存 / 取消 / 分层草稿。
- 欢迎首页首次资源约 50 KB gzip，不加载公司库或其他业务。首次直接进入业务仍需固定公司组件库，公共资源约 1.27 MB（含两种首选图标字体），所选业务合计约 1.32–1.46 MB；冷缓存业务首开仍受网络影响，长期缓存主要改善后续打开与普通刷新。不保证任意网速下固定秒数。后续升级或精简依赖必须另做兼容验证，不能用伪造公司组件替代。
